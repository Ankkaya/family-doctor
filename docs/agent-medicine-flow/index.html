Agent / Control flow

当前查药 Agent：单次请求无循环

没有回到前面节点的边，也没有“模型 → 工具 → 模型”的反复规划循环。意图路由后，问药图沿固定链路运行至 END；急症通过清空候选影响结果，后续节点仍继续执行。

流式遍历 ≠ 工作流循环async for graph.astream 接收各节点结果，async for llm.chat_stream 接收文本片段；它们不回跳到前面的图节点。

再次提问 = 新一轮请求用户追问会重新执行入口与问药图。普通请求可带会话记忆，但不是同一次运行中的自动循环。

失败回退 ≠ 图中的回边普通 NDJSON 流失败时，客户端可再次调用 JSON consult；AG-UI 没有同样回退。这是另一次调用，不是节点闭环。

02 / Candidate retrieval

“找药”实际发生在后端 SQL 中

在 Agent 意图路由之前完成，检索目标是 household_medicine_inventory。

三种信号混合排序

score = 0.55 × 全文得分
　　　 + 0.35 × 向量相似度
　　　 + 0.10 × 关键词命中

全文：ts_rank_cd + plainto_tsquery('simple', query)。向量：1 − cosine_distance。关键词：药名、适应症、别名是否 ILIKE '%完整查询串%'。

向量来自本地确定性特征哈希：词与中文字 → SHA-256 → 384 维带符号累加 → L2 归一化。这里没有调用外部 Embedding 模型。

为什么看起来不相关的药，也可能进入候选？

SQL 的 OR 条件包含 i.embedding IS NOT NULL，因此有向量的库存记录可以进入排序，而非必须命中词语。当前 SQL 没有相似度阈值。随后 match 保留召回结果，真正的适配过滤由 review 中的 LLM 与硬规则完成。20 条上限是后端候选上限，不是最终推荐数量。

03 / Branches & implementation boundaries

读代码时，最容易误解的地方

以下描述当前行为，并不代表已经补齐的产品能力。

A / 同一条问药图

查药与咨询共用工作流

medicine_search 和 medicine_consult 都进入同一 LangGraph。没有独立的“只列出库存”分支。路由为查药/咨询时，即使置信度低或 needsClarification=true，当前分支判断也会继续进入图。

B / 急症分支

清空候选，再走到固定回复

LLM 急症标记或规则关键词命中 → match 的候选变为空 → review 不调用模型 → render 使用固定急症文案、推荐为空。图仍顺序执行后续节点，没有条件边直接跳到 END。

C / 处方药开关

允许开关不解除规则否决

allowRxRecommendation 会传给 review Prompt；但 hard_block_reasons 无条件否决 RX。儿童、孕期、哺乳期也会否决候选推荐。老人标记本身生成警告，并非无条件否决。

D / 多轮记忆接入

AG-UI 与普通请求尚未对齐

普通 ask 加载记忆、扩展检索串并保存返回摘要。AG-UI 后端仅用本轮问题检索；虽然 recent history 被传给路由器，但图初始化不含 history_messages / session_summary / conversation_status，生成摘要也没有回传保存。

E / 文件存在 ≠ 已执行

Top 5 搜索、rank、risk 没有接入

medicine_search.py 中的 search_medicines（Top 5、0.32 阈值）当前没有调用方。rank.py / risk.py 未注册到 builder。该搜索文件只有症状别名字典被 safety_tools 使用。

F / 空结果与失败

没有候选会返回固定文案

无候选或全部被拒绝 → recommends=[]，render 不调用模型，返回未找到匹配药品的固定回复。AG-UI 异常转 RUN_ERROR；普通 NDJSON 流客户端失败可回退到 JSON consult，AG-UI 没有同样的回退。

最终文字回复包含完整药品信息吗？

当前 render 的模型输入只有症状、严重度、候选数量和安全审核警告，未传入逐药名称、剂量与审查原因。药名、适应症、理由、警告通过独立的 recommends 结构返回，用于 App 卡片；不能把自然语言回复与药品卡片当作同一份数据。

状态提示真的表示某一步刚开始吗？

AG-UI 在 graph.astream(..., stream_mode="updates") 返回节点结果后，才发送对应 STEP_STARTED 与状态文案。因此这些提示更多是在报告已返回的阶段；不要用状态到达时间推算节点真实起点。trace 中的 latencyMs 来自节点内部计时。
